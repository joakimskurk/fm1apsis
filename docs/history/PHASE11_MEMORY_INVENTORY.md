## Ordinary RAM accounting

The real JieLi ELF explains Dinghy's RAM metric exactly:
- `.data` payload: **12 B**
- `.bss` payload: **89,700 B**
- alignment gap between `.data` and `.bss`: **4 B**
- `.data` start → `.bss` end span: **89,716 B**

Merged sized-symbol address intervals cover **89,658 B** of that span. The remaining **58 B** is not treated as free RAM; it can be alignment, linker-generated bytes, partially named aggregate storage or other bytes not uniquely represented by sized symbols.

## Static configured stack ranges

The generated linker script exposes:
- `_ustack_lo.._ustack_top`: **24,320 B configured user-stack range**
- 256-B guard before user stack
- `_sstack_lo.._sstack_top`: **7,936 B configured system-stack range**
- 256-B guard before system stack

These stack ranges live after the POOL region and before NOINIT. They are not part of Dinghy's 96-KiB ordinary RAM metric and are not part of the 319,176-B POOL metric.

**These are configured/static ranges only. They are not runtime stack high-water and do not establish physical FM-1 stack headroom.** P11D therefore provides no evidence for shrinking either stack.

## Why P11D does not choose a RAM reduction directly

The largest RAM owners are bounded DSP/runtime pools whose sizes encode musical concurrency, event capacity or implementation topology. A large allocation is not evidence that it is oversized.

In particular, P11D does **not** justify shrinking:
- `bloom_dsp`;
- `apsis_runtime` or the 512-event shared heap;
- `string_transient_pool`;
- Bloom/Spiral audio runtimes;
- configured user/system stacks.

Any such change requires usage/high-water evidence first.

## Next: P11E capacity/high-water stress inventory

P11E should instrument existing bounded capacities without changing them and measure worst observed use under deterministic stress scenarios. Initial targets:
- M3c event heap / queue high-water;
- Bloom DSP voice/occurrence capacity and steals/drops if exposed;
- String transient pool physical/logical high-water, steals and drops;
- Bloom manual/audio queue pressure;
- Spiral audio/runtime slot pressure;
- String Attractor pending/runtime pressure;
- any other large bounded owner that already exposes safe counters or can gain test-only telemetry without altering production scheduling.

P11E is still a measurement phase. Only after a pool has a reproducible worst-case usage envelope with meaningful safety margin should P11F consider a size reduction.

## Verification boundary

P11D proves static ownership from the real JieLi ELF/linker output. It does **not** prove:
- runtime stack high-water;
- physical `app_audio()` ISR/callback cycle margin;
- physical LCD DMA contention;
- physical NOR timing/power-interruption behavior;
- DAC/listening quality.
