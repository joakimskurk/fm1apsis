# TESTING

What is verified, at which level, and how to repeat it. A result is never promoted past the level it was
reached at. Levels: host test < sanitizer < host-mode firmware < real JieLi build < emulator < emulator FM1_STRICT
< physical FM-1. Nothing here is physical-FM-1 verified (no hardware is available).

## The tests

| what | how | level |
| --- | --- | --- |
| APSIS modules: state, runtime, late binding, sources, room, controls, visuals, journal (62 files) | `sh tests/apsis/run.sh` | host + ASan/UBSan |
| the whole firmware (`app.c` + platform) plays scripts; sound pinned | `sh tests/sound.sh` (Linux) | host mode |
| Dinghy's platform: update entry, loader, installer, flash map, packages | `sh tests/run_tests.sh` after `sh build.sh` | host, on the real build |
| the package builds for the JieLi pi32v2; image/RAM/POOL budgets checked by `tools/build.py` | `sh build.sh` | real target build |
| the package on fm1-emu, FM1_STRICT, 20 s scripted performance; the audio interrupt's load | `tests/emu.sh` (CI) | emulator FM1_STRICT |

CI runs all of them on every push to `v2`/`main` and on pull requests.

## Pinned sound (tests/sound.sha256)

The host-mode WAVs of `default` (Dinghy's script), `tests/scripts/apsis_transport.txt` (transport stop/start,
every surface, 19 s) and `tests/scripts/apsis_perform.txt` (String plucks, Bloom petals and grow, Gravity, SPACE,
knobs). On 2026-11-02 the first two were **bit-identical** to the old P11W app (generated by the old
`ci/apply_apsis_p10g.sh` chain on Dinghy 0.3, built in host mode with shims), so v2 changed nothing audible.
gcc and clang builds of the host firmware give identical WAVs (checked 2026-11-02).
A change to these hashes must be deliberate: `UPDATE=1 sh tests/sound.sh` and the reason in the commit.

## A compiler-dependent bug, found and fixed (2026-11-02)

`apsis_runtime.c` passed two `m3c_random()` draws as arguments of one call (Bloom's voicing walk and pick). C
leaves the order open: gcc drew pick first, clang (and so JieLi's clang, the firmware) walk first. The old CI ran
its host tests with gcc, so it tested a different Bloom voicing than the FM-1 played. The draws are now sequenced
(walk, then pick, as `bloomChooseVoicingPlan` in Study 126). The tests run with both compilers (CI: gcc;
macOS: clang). Two Phase-5 tests that relied on one seed's random pick now check several seeds.

## Emulator load

`tests/emu.sh` fails if any audio block takes 5805 us or more (a drop-out) or if the audio stalls; it warns over
50 %. It reads the firmware's probes from a RAM dump: the load, the worst block by part, each part's worst, the
blocks over 80 % / 100 % and the voices' high water. `PROFILE=1 tests/emu.sh` on the `-fno-inline` build prints the
cycles per function (CI's emulator job does both).

| date, commit | avg | worst | blocks over 100 % |
| --- | --- | --- | --- |
| 2026-11-02 92dbd5e (= P11W's audio) | 188 % | 209 % | ~half lost |
| 2026-11-02 5918797 (v2.1) | 44.0 % | 69.8 % | 0 |
| 2026-11-02 ca04914 STRESS build (every source densest) | 302 % | 483 % | 964 of 970; audio collapses |
| 2026-11-02 v2.2-margin (B, exact): normal | 43.5 % | 60.9 % | 0; the bound 95.9 % (was 113.8 %) |
| 2026-11-02 v2.2-margin (B, exact): STRESS | 229 % | 389 % | still collapses: 58 Bloom petals |

## Known gaps

- host mode feeds keys and buttons but not every interaction the panel allows (held combinations are partial)
- FM1_STRICT is a cycle model, not the chip: the real margin, USB/key-scan interrupt cost and LCD/audio bus
  contention remain unverified until an FM-1 runs it
- no power-cut test of the journal on real NOR (fm1-emu's FM1_FLASH_CUT could cover the emulated part)
